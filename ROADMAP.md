## Этап 2: Workflow движок (QwenFlow)

**Срок:** 6-8 недель
**Приоритет:** 🔴 Критический

### Текущее состояние:
- ❌ Отсутствует

### Целевое состояние:
Декларативные workflow в YAML/JSON с поддержкой:
- Детерминированного выполнения
- Шагов утверждения (approval gates)
- Возобновления после паузы
- Конвейеров данных между шагами

### Задачи:

- [ ] **2.1** Спроектировать формат workflow (YAML)
- [ ] **2.2** Реализовать парсер workflow
- [ ] **2.3** Создать runtime для выполнения шагов
- [ ] **2.4** Добавить шаги утверждения (approval required)
- [ ] **2.5** Реализовать токены возобновления (resume tokens)
- [ ] **2.6** Добавить систему переменных и шаблонов
- [ ] **2.7** Создать CLI для запуска workflow
- [ ] **2.8** Реализовать планировщик (cron + webhooks)

### Пример workflow:

```yaml
# weekly-report.yaml
name: weekly-report
description: Еженедельный отчёт по проекту
version: "1.0"

args:
  project_path: string
  output_format: string

steps:
  - name: get-commits
    tool: git-log
    args:
      repo: "{{args.project_path}}"
      since: "7 days ago"

  - name: analyze-changes
    tool: llm
    args:
      model: "qwen"
      prompt: |
        Проанализируй изменения:
        {{get-commits.output}}

  - name: generate-summary
    tool: llm
    args:
      model: "qwen"
      prompt: |
        Создай недельную сводку:
        {{analyze-changes.output}}

  - name: send-report
    tool: telegram
    args:
      chat_id: "@team"
      message: "{{generate-summary.output}}"
    approval: required

triggers:
  - cron: "0 9 * * 1"  # Каждый понедельник в 9:00
  - webhook: "/trigger/weekly-report"
```

### Метрики успеха:
- ✅ 5+ готовых workflow шаблонов
- ✅ Approval steps работают
- ✅ Resume tokens сохраняются
- ✅ Cron + webhooks работают

## Этап 3: Улучшенная система памяти

**Срок:** 4-6 недель
**Приоритет:** 🔴 Критический

### Текущее состояние:
- PostgreSQL + pgVector для векторного поиска
- Redis для кэширования
- Нет файлового представления памяти

### Целевое состояние:
Гибридная система:
- Markdown файлы как основной формат (человекочитаемый)
- Векторный поиск по содержимому
- Многоуровневая архитектура памяти

### Задачи:

- [ ] **3.1** Определить структуру памяти (Markdown файлы)
- [ ] **3.2** Создать файлы: `MEMORY.md`, `SOUL.md`, `HEARTBEAT.md`
- [ ] **3.3** Реализовать ежедневные логи (`memory/YYYY-MM-DD.md`)
- [ ] **3.4** Добавить гибридный поиск (vector + BM25)
- [ ] **3.5** Реализовать compaction контекста
- [ ] **3.6** Добавить инструменты работы с памятью (`memory_search`, `memory_get`)
- [ ] **3.7** Создать систему тегирования и категоризации

### Архитектура памяти:

```
┌─────────────────────────────────────────────────────────┐
│ Layer 4: Semantic Vector Search                         │
│ SQLite + embeddings (поиск по смыслу)                   │
├─────────────────────────────────────────────────────────┤
│ Layer 3: Long-term Memory (MEMORY.md)                   │
│ Курируемые факты, решения, предпочтения                 │
├─────────────────────────────────────────────────────────┤
│ Layer 2: Daily Logs (memory/YYYY-MM-DD.md)              │
│ Сырые ежедневные заметки (append-only)                  │
├─────────────────────────────────────────────────────────┤
│ Layer 1: Session Context (JSONL)                        │
│ Текущая конверсация в контекстном окне                  │
└─────────────────────────────────────────────────────────┘
```

### Метрики успеха:
- ✅ Память сохраняется между сессиями
- ✅ Гибридный поиск работает (<100ms)
- ✅ Compaction автоматически срабатывает
- ✅ Markdown файлы читаемы человеком
